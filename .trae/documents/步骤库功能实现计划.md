# 步骤库功能实现计划

## 一、需求概述

实现一个步骤库功能，允许用户在测试流程执行成功后选择将步骤保存到步骤库中。保存流程：
1. 将执行过程转换为可重放的脚本（MCP 工具调用序列）
2. 自动执行 3 次验证脚本稳定性
3. 验证通过后存储到 IndexedDB
4. 支持从步骤库直接点击重新执行

## 二、当前架构分析

### 核心文件
- `app/api/chat/route.ts`: 测试执行主流程，包含 LLM 调用和 MCP 工具执行
- `app/components/ChatDrawer.tsx`: 测试面板 UI 组件
- `app/page.tsx`: 主页面，包含打开测试面板的按钮

### 当前执行流程
1. 用户输入测试需求 → LLM 决策
2. LLM 返回 tool_calls（包含工具名和参数）
3. 执行 MCP 工具调用（browser_navigate, browser_click 等）
4. 循环直到测试完成

### 关键数据结构
```typescript
// tool_calls 结构
{
  id: string,
  function: {
    name: string,        // 工具名，如 "browser_click"
    arguments: string    // JSON 字符串，包含参数
  }
}
```

## 三、实现方案

### 3.1 数据模型设计

#### 步骤库存储结构（IndexedDB）
```typescript
interface TestStep {
  id: string;              // UUID
  name: string;            // 步骤名称（用户可编辑）
  originalTask: string;    // 原始测试需求

  createdAt: number;       // 创建时间戳
  successCount: number;    // 成功执行次数
  lastExecutedAt?: number; // 最后执行时间
}

interface ToolCall {
  toolName: string;        // 工具名称
  arguments: any;          // 工具参数
  description?: string;    // 可选描述
}
```

### 3.2 核心功能模块

#### 模块 1: 脚本收集器
**文件**: `app/utils/scriptCollector.ts`

功能：
- 在测试执行过程中收集所有的 tool_calls
- 过滤掉非必要的工具调用（如重复的 browser_snapshot）
- 生成可重放的脚本序列

关键逻辑：
```typescript
class ScriptCollector {
  private toolCalls: ToolCall[] = [];
  
  addToolCall(toolName: string, args: any) {
    // 过滤重复的快照查询
    if (toolName === 'browser_snapshot' && this.isDuplicateSnapshot()) {
      return;
    }
    this.toolCalls.push({ toolName, arguments: args });
  }
  
  getScript(): ToolCall[] {
    return this.toolCalls;
  }
}
```

#### 模块 2: 脚本执行器
**文件**: `app/utils/scriptExecutor.ts`

功能：
- 接收脚本序列（ToolCall[]）
- 按顺序执行每个工具调用
- 不经过 LLM 决策，直接重放
- 返回执行结果（成功/失败）

关键逻辑：
```typescript
async function executeScript(
  script: ToolCall[],
  mcpClient: Client,
  onProgress?: (step: number, total: number) => void
): Promise<{ success: boolean; error?: string }> {
  for (let i = 0; i < script.length; i++) {
    const { toolName, arguments: args } = script[i];
    onProgress?.(i + 1, script.length);
    
    try {
      await mcpClient.callTool({ name: toolName, arguments: args });
    } catch (error) {
      return { success: false, error: error.message };
    }
  }
  return { success: true };
}
```

#### 模块 3: IndexedDB 存储层
**文件**: `app/utils/stepLibraryDB.ts`

功能：
- 封装 IndexedDB 操作
- 提供 CRUD 接口
- 管理步骤库数据

关键 API：
```typescript
// 添加步骤
async function addStep(step: TestStep): Promise<void>

// 获取所有步骤
async function getAllSteps(): Promise<TestStep[]>

// 删除步骤
async function deleteStep(id: string): Promise<void>

// 更新步骤执行统计
async function updateStepStats(id: string, success: boolean): Promise<void>
```

#### 模块 4: 自动验证器
**文件**: `app/utils/scriptValidator.ts`

功能：
- 执行脚本 3 次验证稳定性
- 每次执行前重置浏览器状态
- 收集执行结果

关键逻辑：
```typescript
async function validateScript(
  script: ToolCall[],
  mcpClient: Client,
  times: number = 3
): Promise<{ valid: boolean; successCount: number }> {
  let successCount = 0;
  
  for (let i = 0; i < times; i++) {
    // 重置浏览器状态（导航到空白页）
    await mcpClient.callTool({
      name: 'browser_navigate',
      arguments: { url: 'about:blank' }
    });
    
    const result = await executeScript(script, mcpClient);
    if (result.success) {
      successCount++;
    }
  }
  
  return { valid: successCount === times, successCount };
}
```

### 3.5 执行流程

#### 流程 1: 保存步骤到步骤库
```
1. 用户执行测试任务
2. 测试成功完成
3. 显示"保存到步骤库"按钮
4. 用户点击按钮，输入步骤名称
5. 后端收集执行过程中的 tool_calls
6. 自动验证：执行脚本 3 次
7. 验证通过后保存到 IndexedDB
8. 显示成功提示
```

#### 流程 2: 从步骤库执行
```
1. 用户打开步骤库抽屉
2. 选择要执行的步骤
3. 点击"执行"按钮
4. 后端读取保存的脚本序列
5. 直接执行脚本（不经过 LLM）
6. 显示执行进度和结果
7. 更新步骤的执行统计
```

## 五、技术决策

### 决策 1: 脚本定义
**选择**: MCP 工具调用序列（ToolCall[]）
**理由**: 
- 复用现有的 MCP 工具执行机制
- 不需要转换到 Playwright 代码
- 保持与现有架构的一致性

### 决策 2: 存储方案
**选择**: IndexedDB
**理由**:
- 浏览器原生支持，无需额外依赖
- 支持结构化数据存储
- 容量充足，适合存储脚本序列

### 决策 3: 验证策略
**选择**: 执行 3 次完整脚本
**理由**:
- 确保脚本稳定性
- 发现偶发性问题
- 提高步骤库质量

### 决策 4: UI 形态
**选择**: 独立抽屉组件
**理由**:
- 与测试面板分离，职责清晰
- 不占用测试面板空间
- 可随时打开查看步骤库

## 七、风险与缓解

### 风险 1: 元素引用失效
**问题**: MCP 工具调用中的 ref 是动态的，重新执行时可能失效
**缓解**: 
- 在执行器中添加智能重试机制
- 如果 ref 失效，尝试通过其他属性（如文本、位置）定位元素
- 验证阶段发现此类问题，不保存不稳定的脚本

### 风险 2: 页面状态不一致
**问题**: 每次执行时页面初始状态可能不同
**缓解**:
- 每次验证前重置浏览器到空白页
- 在脚本开头添加导航到起始页面的步骤
- 要求用户从一致的初始状态开始执行

### 风险 3: IndexedDB 兼容性
**问题**: 某些浏览器可能不支持 IndexedDB
**缓解**:
- 使用成熟的 IndexedDB 封装库（如 idb）
- 添加降级方案（localStorage）
- 在 UI 中提示浏览器兼容性
